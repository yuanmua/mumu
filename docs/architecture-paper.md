# 沐沐内核：一个面向数字角色的机制/策略分离运行时

> 内核 v1.0 · 定档 2026-08-18 · 实现见 [`src/kernel/`](../src/kernel)
> 配套：[handbook.md](handbook.md)（约定与决策记忆）· [kernel.md](kernel.md)（使用参考）

---

## 摘要

本文描述沐沐（Mumu）内核的设计。它要解决的问题是：**如何构造一个数字角色运行时，使得角色的一切具体形态——用什么模型、有什么动作、什么性格、在哪出现、怎么说话——都可以在不修改内核的前提下被替换。**

核心主张是把内核收缩为**九个机制**，共约 1900 行，其中不含任何模型提供方、动作、表情、会话形态、存储介质，乃至任何一句面向用户的自然语言。所有这些都由插件贡献。

内核的判别标准只有一句：**换一个插件能不能换掉它？** 能，它就不属于内核。

在此约束下，本文论证四项设计选择是必要而非任意的：

1. **两端对称的开放信封**——输入与输出使用同构的、语义不透明的信封，节拍固定而内容开放；
2. **实际送达前缀（delivered prefix）**——被打断时，日志记录对方真正收到的部分而非模型生成的全文；
3. **编排与发声分离**——决策器只产出意图，不产出话语；
4. **可撤销注册**——一切贡献都返回撤销函数，使热重载与卸载成为同一机制的两种用法。

## 1. 引言

### 1.1 问题

一个数字角色系统面临的困难不在于"接一个大模型让它说话"，而在于以下几点同时成立：

- 角色要接入**形态各异的表现端**：命令行、网页、语音、Live2D、群聊、弹幕、游戏；
- 它必须是**流式**的，并且**可以被打断**，被打断后还要能正确接话；
- 它要**会用工具**，且用工具时不能把话卡住；
- 上面这些都要能**长期演化**——今天的模型、协议、渲染方式在一年后都会变。

朴素做法是把这些能力堆进一个大循环，用配置开关区分场景。其失效模式是可预测的：每加一种模态就要改核心，每加一种会话形态就要加分支，最终核心变成一个没人敢动的泥球。

### 1.2 论点

真正的分界不在"功能大小"，而在**机制（mechanism）与策略（policy）**：

> **机制**是"话怎么被打断、什么必须被记录、一拍如何被唤醒"——它们定义了插件赖以存在的场地。
> **策略**是"怎么想、记什么、什么表情、在哪出现"——它们是场地上的玩法。

内核只实现机制。这不是审美偏好，而是一个可操作的判据：**若某物可以被一个插件替换掉，它就是策略，不得进入内核。**

本文其余部分展示：在严格执行这条判据后，内核收敛到什么形状，以及为什么某些看起来像"功能"的东西（送达回执、空拍熔断、可撤销注册）实际上是不可省略的机制。

## 2. 设计原则

### P1 机制/策略分离

已如上述。这条派生出一个反直觉的推论：**内核不得包含任何一句面向用户的自然语言**。因为"唤醒原因该怎么写""工作记忆该怎么呈现"都是可替换的呈现策略。内核只输出结构化数据（`WakeReason{source, text, channel, sender}`、`Note{source, text, elapsedMs}`），渲染交给消费方。

### P2 结构位而非语义

内核需要对输入做**某些**判断（要不要打断、要不要进历史），但它不能理解输入的含义。解法是：内核只读**结构位**（structural bits）——若干与语义无关的字段——而绝不解析 `kind` 这类由插件定义的自由字符串。

| 结构位 | 内核据此做的唯一决定 |
|---|---|
| `text` + `sender` | 是否进入对话历史 |
| `channel` | 路由到哪些表现端；打断切哪个频道 |
| `urgent` | 是否硬打断本频道发声 |
| `Part.text` | 是否计入送达账 |
| `external`（唤醒） | 是否豁免退避、是否解除熔断 |

于是"群聊""弹幕""视觉帧""文件"对内核完全等价，都是带不同 `kind` 的信封。**增加一种会话形态不需要内核知情。**

### P3 唯一真源

会话日志是 append-only 的事件序列，模型历史、界面、回放、统计全部由它投影，不存在第二份状态。落盘本身是插件的事（存储 seam），内核只持内存镜像并定义持久化契约。

### P4 降级优于崩溃，且降级必须可见

任何单点失败（段落渲染、事件监听、表现端、拦截器、决策器、落盘）都不得终止角色；但每一次降级都要留下可检索的痕迹（`console.error` + 日志事件）。静默降级与崩溃同样有害。

### P5 注册即可撤销

一切贡献——服务、段落、动作类型、marker 词汇、事件监听、拦截器——都通过返回撤销函数的 effect 安装。由此，"卸载插件"与"热重载插件"是同一机制的两种用法，无需为热重载单独设计。

                    └───────┬──────────────────────────┬─────────────┘

        │  prompt — 段落贡献 / 工作记忆                              │
        │  llm — 角色绑定网关 / 流原语与 marker 解析                  │

        ┌───────────────────────────────────────────────────────────┐

九个机制，依赖自下而上单向。`mumu.ts` 是唯一知道全貌的文件，负责把它们用窄接口接线；机制之间不互相 import 实现。

## 4. 机制详述

### 4.1 容器（core/container）

服务占据稳定的键（`ctx.bus`、`ctx.log`、`ctx.io`…），插件按键查找而非 import 实现。插件声明 `inject` 依赖，容器反复扫描待激活队列直到无进展——**加载顺序由依赖推导，不由手写启动序列决定**。

三条性质：

- **失败不留半成品**：`apply` 抛错时立即卸载该插件，已注册的 effect 逆序回滚。
- **卸载精确回滚**：disposer 逆序执行，服务撤销，监听移除。
- **依赖未满足要可见**：`unresolved()` 暴露悬空插件，装配层据此大声失败而不是静默少装一个插件。

### 4.2 总线（core/bus）

两种分发模式，且只有两种：

**emit** —— 通知，不等待，监听器错误互相隔离。语义是"观察已发生的事实"。

**waterfall** —— 环绕中间件。拦截器接收 `(payload, next)`，改写共享 payload 后调用 `next()` 委托；不调 `next` 即短路。**终端（terminal）是内核的默认行为**，因此拦截器天然可以包裹、改写、或整个替换内核决定。

这个设计是"插件能改一切"与"插件能改插件"的共同载体：任何可被改变的决定，都以 waterfall 形式暴露；插件想让自己被别人改，就把自己的决定也放到 waterfall 上（官方 CLI 的 `cli/render` 即是范例，主题插件拦截它改样式，双方互不 import）。

内核当前暴露四条水线：

| 水线 | 决定什么 |
|---|---|
| `percept/pre-beat` | 感知是否打断发声、是否唤醒 |
| `beat/gather` | 一拍能看到什么材料 |
| `intent/pre-dispatch` | 意图是否放行、参数如何改写 |
| `expression/pre-emit` | 输出是否放行、如何改写 |

链在调用时快照，因此热重载不影响在途调用。`next()` 被重复调用会抛错——这是一类真实且难查的插件 bug。

### 4.3 贡献集合（core/registry）

"插件往集合里放东西"被抽象为单一机制。内核自用三处（段落、动作类型、marker 词汇），插件 `provide` 一个 `Registry` 即开出新扩展点，无需手写注册表。

提供唯一键（`keyOf`）时键唯一、重复注册大声失败（段落、动作类型）；不提供时允许重复（marker 词汇——多个插件贡献同名表情是常态）。

### 4.4 会话日志（session/log）

**三条不变量**，它们是整个系统正确性的基石：

> **I1 模型可见 ⟺ 已记录。** 任何进入模型请求的东西必须能从日志重建。
> **I2 说出去的 ⟺ 记录实际送达的部分。** 打断时记 delivered 前缀，不记生成全文。
> **I3 `action.started` 必有 `action.ended`。** 孤儿在挂载存储时补记 `interrupted`。

I1 的实践后果被低估：它意味着**新增一种模型可见输入就必须新增一种日志事件**。这条约束反过来塑造了流式感知的设计（§4.9）——因为在途内容对决策器可见，它就必须落日志。

I3 的处理方式值得一提：孤儿不是被静默清理，而是回调到装配层，转化为角色的一条工作记忆（"上次运行时这些动作被强行中断了"）。**崩溃恢复被表达为角色的自我察觉**，而不是运维细节。

历史投影是纯结构规则：带 `text` 与 `sender` 的感知 ⇒ 对方侧；`utterance.settled` 的 `delivered` ⇒ 自己侧。它不认任何 `kind` 语义。想要更丰富投影的插件直接读事件流自行投影。

**清除记忆**是显式的生命周期操作而非普通写入：`reset()` 使真源归零，并通过 `onReset` 回调让装配层连带清空工作记忆——调用方只需一处调用，不会出现"日志清了但工作记忆还记得"的不一致。

### 4.5 模型网关（llm/gateway）

内核零 provider。插件不接触具体模型，只声明**角色**（`mind.decide`、`performer`、`memory.summarize`…），由配置把角色绑定到 provider + model + 参数。

这带来四项收益，每项都难以用其他方式获得：

1. 换模型改一处配置，任何插件不必改动；
2. 预算、限流、降级链有统一的落点；
3. 插件消耗的 token 同样记账进日志——"钱花在哪"可查；
4. 同一角色在不同部署可绑不同档次的模型（本地小模型 / 云端大模型）。

逐 chunk 的观察走 `model.stream` **emit 而不落日志**——因为内容已被 `model.request`/`model.response` 覆盖，重复记录只会膨胀真源。这里体现一条判别：**要改行为用 waterfall，要看事实用 emit；只有构成事实的才落日志。**

### 4.6 流原语（llm/stream）

统一的 `StreamChunk` 词汇，以及 `<|track:body|>` 内联标记的流式解析。

解析器的关键在于**尾部缓冲**：当缓冲区尾部可能是开标记的前缀（`<`）时，保留该字符不外发，避免把半个标记当作正文吐出。另设未闭合长度上限，超限即按普通文本吐出，防止模型意外输出 `<|` 导致流永久卡死。

内核只认识标记的**语法**，不认识任何标记的**含义**——`emo`、`act`、`tool` 分别意味着什么，由插件贡献的词汇表定义。

### 4.7 心跳调度（mind/scheduler）

**一拍（beat）= 一次决策器睁眼**：汇聚材料 → 决策器产出意图 → 派发到动作层。拍本身不产生任何面向用户的输出。

调度不是定时轮询，而是**被唤醒**的。唤醒源包括感知、动作收尾、定时器。三重防护共同抑制自激振荡：

- **合流**：冷却窗口内的多次唤醒合成一拍，原因结构化累积；
- **同源指数退避**：内生唤醒（动作收尾）逐次放缓至上限；外部唤醒（感知、定时器）永不退避；
- **空拍熔断**：连续若干拍无产出即进入静默，此后只接受外部唤醒。

"等待"不是动作，而是**空意图 + 定时器**。此前的原型把 `wait` 实现为动作，代价是它占用动作槽位、需要特判"打断 wait"、"连续等待"需要单独计数——改为调度状态后这些复杂度一并消失。这是一个"把策略误当机制"被纠正的实例。

材料是开放的：内核只填自己知道的部分，随后过 `beat/gather` 水线，插件往 `blocks` 贡献任意材料。每块材料同时携带**自然语言 `text`（任何决策器都能渲染）与结构化 `data`（给认识它的决策器）**。记忆、情绪、外部状态都走这条路而内核不必认识它们。

汇聚过程本身可能因插件抛错而失败。由于 `beat()` 是 fire-and-forget 调用的，未捕获拒绝会终止进程，因此汇聚失败被内部捕获、记为 `beat.failed`、作废本拍且不重试——下一次唤醒会带冷却重新开拍。

### 4.8 动作层（actions/registry）

**决策器只编排，不发声。** 实际的说话与做事都发生在动作实例里。

这一分离的收益是结构性的：

- 决策器输出极短（数十 token），因而可以用较贵的模型而延迟可控；
- 发言被硬打断不影响决策器的状态机；
- "说话中并行做事"自然成立——发言与工具是两个并发的动作实例，而不是一个串行的 agent 循环。

动作类型由插件注册，实例可多开并发（`reply#1`、`reply#2`）。实例携带频道，发声默认回该频道，**不存在"最近一次感知的频道"这类全局可变状态**——此前存在过，多频道并发会串台，已移除。

完成、失败、被停一律回灌为唤醒原因。**动作失败因此成为一种感知**：角色"意识到"自己出了什么事，如何面对由决策器决定，而不是被运行时静默吞掉。

### 4.9 IO 端口（io/port）

内核与外界的全部接触面。

**两端对称的开放信封。** 这是全套设计中最关键的一条：

```
Percept { kind, channel?, sender?, text?, urgent?, data? }   ← 进
Part    { kind, text?, data? }                                ← 出
```

`kind` 两侧都是自由字符串，内核不认识任何一种模态。**固定的只有节拍，且两端都是流**：

```
进：Perception = 若干 update → end，或中途 cancel
出：Utterance  = 若干 part   → end，或中途 stop
```

这一对称性曾两次被破坏，两次都构成真实缺陷：

- 早期 `Expression` 是封闭联合（`speech.chunk | marker | stop`）。`speech` 一词本身即模态假设，增加图片、音频、游戏指令都要改内核。**输入开放而输出封闭，是伪装成通用的具体。**
- 修正后，输入仍只有一次性的 `Percept`。逐字语音输入会刷屏日志、每个字进一条历史。**输出是流而输入是离散，是同一错误的镜像。**

`Perception.update` 的语义是**修订**而非追加：语音识别的中间结果后一次覆盖前一次。取修订是因为修订可以表达追加（传累计文本），反之不能。

音频与视频帧不进内核：表现端完成识别后再把文本流入——与输出端"内核流文本、语音合成在表现端"是同一层分工。

**能力降级只有一条规则**：表现端不认识的 `Part.kind` 直接忽略。没有第二条。

**双向打断**：

| 方向 | 机制 |
|---|---|
| 对方打断角色 | `urgent` ⇒ 硬停本频道发声 ⇒ 按回执记录实际送达前缀 |
| 角色打断对方 | 在途感知进入一拍材料，决策器看得见"谁在说、说了多久、说到哪"，可直接发起发言 |

流式输入的唤醒是**按需**的：只有显式请求时才开一拍，否则每个字一拍将不可承受。何时值得唤醒（停顿、关键词、说得过久）是表现端与插件的策略。

**在途状态的兜底**：两侧都有防泄漏时限——发声有结算超时，感知有兜底取消（有动静即续期，只有真正卡死才被取消）。这类记账定时器一律不阻止进程退出。关机时两侧一并收尾，日志不留半开的记录。

## 5. 实际送达前缀

这是内核中最容易被忽略、却最不可省略的一条机制，值得单独论述。

### 5.1 问题

角色说到一半被打断。此时存在两个不同的文本：模型**生成**的全文，与对方**实际收到**的前缀。

若日志记录前者，则下一轮模型会认为自己已经说过了后半段。对语音角色而言这必然发生——用户只听到"明天天气是晴"，模型却以为自己说完了"气温十七度"，于是接话时不再重复，而用户从未听到。

### 5.2 机制

表现端声明是否具备回报能力，并在呈现过程中回报累计送达量。硬打断时，内核以回报快照截断生成文本，记为 `utterance.settled { delivered, truncated, cause }`。历史投影只取 `delivered`。

不具备回报能力的表现端按全量记账，但其能力声明中已注明——**账目可能不精确，但不会说谎**。

送达账的通用规则是：**只有 `Part.text` 计入**。文本是线性可截断的，其余片段（图片、卡片、指令）是原子的。这使得该机制在任意模态下都成立。

### 5.3 讨论

发言动作在收尾时把结果写入工作记忆——包括"实际说出的"与"没说出去的"两部分。这使得"接话不重复"从一个需要模型自觉的要求，变成了一条摆在上下文里的事实。

这一环节很容易被忽略，原因大概是：在纯文字场景下，打断的粒度较粗，问题不易暴露；只有当语音与打字机式呈现介入，生成与送达的差距才变得显著。

## 6. 失效模型

| 失效点 | 处理 | 可见性 |
|---|---|---|
| 段落渲染抛错 | 缺该段，其余照常组装 | `console.error` |
| 事件监听器抛错 | 隔离，不影响其他监听器与发射方 | `console.error` |
| 拦截器抛错 | 降级为默认行为，**不吞掉输入** | 日志 `percept.route-error` |
| 汇聚材料抛错 | 作废本拍，不重试 | 日志 `beat.failed` |
| 决策器抛错 / 输出不合形态 | 重试一次，再失败则空意图 | `console.error` + 日志 |
| 动作实例崩溃 | 进入错误态并**回灌为感知** | 日志 `action.ended{error}` |
| 表现端抛错 | 隔离，其他端照常接收 | `console.error` |
| 落盘失败 | 不打断角色 | `console.error` |
| 在途状态卡死 | 兜底时限自动收尾 | 日志 + 警告 |

一条贯穿的原则：**fire-and-forget 调用点必须自己兜住错误**。在 Node 中未捕获的 Promise 拒绝会终止进程，因此被 `void` 调用的内核方法（感知路由、开拍）承诺不抛出。

## 7. 与相关工作的关系

本内核在三处借鉴了成熟设计，并在两处刻意背离。

**借鉴。** 服务容器 + 依赖声明 + 可撤销注册、环绕中间件、append-only 日志作为唯一真源，取自插件化 agent 框架的成熟实践；内联标记的流式安全解析取自数字角色项目；决策器只编排不发声、工作记忆的双重衰减与时间标注，取自自研原型。

**背离一：不整体引入既有框架。** 引入一个完整的插件框架等于引入一个不受本项目控制的内核。本内核需要的只是容器、总线、effect 三件事，自行实现约数百行，换来的是可以按角色场景精确塑形（例如打断信号穿透中间件链、记账定时器不阻塞退出）。

**背离二：不采用 turn/step 节拍。** 面向代码任务的 agent 框架以"轮次—步骤"为节拍：收到任务，反复请求模型直到无欠工作。数字角色不是这个形态——它可能什么都不做，可能同时说话与查询，可能说到一半被打断，可能无人说话时自行想起某事。因此节拍单位取"一次决策器睁眼"，且拍本身不产生输出。

## 8. 局限

以下为已知且被接受的取舍，非缺陷：

- **打字机式呈现下的打断存在一次写入的误差**：结算使用打断瞬间的回报快照，终端可能多显示一个字符。为此加锁不划算。
- **多个表现端服务同一频道且能力不一致时**，`delivered` 以具备回报能力者为准。
- **决策器是独占槽位**：装载第二个决策器插件会大声失败，需先卸载。这是有意的——两个大脑没有合并语义。
- **热重载只突破入口文件的模块缓存**：多文件插件修改深层文件需重启，或把状态收敛到入口。
- **`history()` 是便利投影而非机制**：其结构规则写死了两个事件类型；需要更丰富投影的插件应直接读事件流。
- **多实例已具备结构基础但未实践**：`Mumu.create()` 每次构造独立的一棵树，跨实例通讯尚无机制。

## 9. 定档：冻结的契约

内核 v1.1 冻结以下契约（v1.0 → v1.1 是开源前的最后一次调整，逐条理由见 [handbook.md](handbook.md) §9.3）。
修改它们属于破坏性变更，需同步更新 handbook 的决策记忆一节，并升 `KERNEL_VERSION`。

**类型契约**：`Percept` · `Part` · `MediaFields` · `Perception` · `Utterance` · `Expression` · `Surface` · `Intent` · `Decision` · `BeatMaterial` · `MaterialBlock` · `WakeInput` · `HistoryTurn` · `Note` · `Section` · `ActionType` · `ActionRun` · `Outcome` · `ChatMessage` · `ProviderAdapter` · `RoleBinding` · `LogStore` · `BlobStore` · `Feedback` · `Plugin`

**不变量**：I1（模型可见 ⟺ 已记录）· I2（说出去的 ⟺ 记录实际送达）· I3（动作起止成对）

**日志身份**：每段日志以 `log.opened { boot, kernel, schema, cause }` 开头；动作 / 发声 / 感知 / 模型请求的 id = 「前缀#起始事件序号」，同一份日志里永不重复；
内核发的唤醒与工作记忆带 `data.code`，不拼人话。

**扩展点**：四条水线（`percept/pre-beat`、`beat/gather`、`intent/pre-dispatch`、`expression/pre-emit`）· 两个观察事件（`log.appended`、`model.stream`）· 七个服务键（`bus` `log` `model` `mind` `actions` `prompt` `io`）· 一个由插件提供、内核定契约的服务键（`blobs`）

**边界**：内核对外只经 `kernel/index.ts` 一个出口；插件只从 `src/index.ts` 导入。两条边界均有测试守护。

**装配无全局配置**：入口裸启内核，装什么插件由 `plugins/` 目录决定，各插件默认配置写在自己的
`package.json`（`mumu.defaults`），运行期改动存入配置库。**没有中心化的配置文件，也没有环境变量**——
这使得"增删一个插件"是纯粹的目录操作，不需要在别处登记。

**可继续演化而不破坏契约的**：机制内部实现、`KernelOptions` 新增字段、新增水线与观察事件、新增结构位（可选字段）、新增日志事件类型。

## 10. 结语

本内核的全部主张可以压缩为一句：**把"什么必须为真"与"该做什么"分开，前者进内核，后者进插件。**

前者是少数几条——话被打断时账目必须诚实、模型看见的必须可重建、注册必须可撤销、一拍必须被唤醒而非轮询。后者是无穷多——用哪个模型、什么性格、什么表情、在哪出现、怎么记忆、怎么思考。

内核的价值不在于它能做多少，而在于它**拒绝**做多少：它不认识群聊，不认识语音，不认识表情，不认识 SQLite，不会说一句中文。正因如此，这些东西才能被自由地加进来、换掉、拿走。
